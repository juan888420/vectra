# Resumen del proyecto

> Se actualiza al final de cada sesión. Léelo primero para saber dónde retomar.

**Última actualización**: 2026-07-30 (ADR-0006: interfaz orientada a preguntas financieras, no a CRUD)

## Estado

**Backend**: completo para el ledger — auth (JWT + refresh), accounts, categories, transactions, budgets, recurring-transactions (con processor idempotente), dashboard y reports — y ahora también para el dominio de escenarios: expense-items, incomes (RFC-0021) y scenarios (RFC-0022). Todo en `apps/api`, con tests de integración. Nuevos registros usan `COP` como `defaultCurrency` por defecto (antes `USD`; el usuario de prueba sembrado sigue en USD, no se tocó).

**Escenarios (RFC-0022)**: `Scenario` (estados `ACTIVE`/`INACTIVE`/`ARCHIVED`) con `ScenarioItem`/`ScenarioIncome` como snapshots explícitos de `ExpenseItem`/`Income` — el escenario nunca lee el recurso original en vivo, así que un cambio de precio nunca modifica una simulación en silencio (ADR-0005). `ScenarioComposition` permite escenario-en-escenario con detección de ciclos (BFS en service layer, no SQL recursivo). `GET /scenarios/:id/summary` calcula, siempre derivado y nunca almacenado: totales mensual/6m/12m (prorrateo de `YEARLY` ÷12, `ONE_TIME` aparte), cobertura de ingresos (% consumido, restante) y `hasUpdates` (compara `lastSyncedAt` del snapshot contra el `updatedAt` del `ExpenseItem`/`Income`/categoría original; se propaga transitivamente a través de la composición). `deleteExpenseItem`/`deleteIncome` ahora bloquean el borrado físico si un `ScenarioItem`/`ScenarioIncome` los referencia (archivar en su lugar). El endpoint de sincronización (aplicar el precio/nombre nuevo al snapshot) queda pospuesto al RFC del composer/frontend, que es quien lo va a consumir.

**Frontend**: infraestructura (RFC-0017) + UI de negocio para Accounts/Categories (RFC-0018) + Transactions (RFC-0019) + Dashboard (RFC-0020, mergeado vía PR #16) + **Productos/Ingresos/Escenarios (Fase 2, puntos 3-4)**. Vite + React 19 + Tailwind v4, `packages/ui` (shadcn/ui: `Table`/`Dialog`/`Select`/`Badge`/`AlertDialog`/`Skeleton`/`Card` + `DataTable`/`EmptyState`/`FormDialog` reutilizables), `packages/types` (schemas Zod compartidos: `accounts`/`categories`/`transactions`/`budgets` (parcial, solo lectura)/`dashboard`/`money`/`expense-items`/`incomes`/`scenarios`) y `packages/utils` (`formatMoney`/`formatDateOnly` compartidos). Auth flow verificado end-to-end. CRUD completo de Accounts, Categories, Transactions, **Expense Items (Productos) e Incomes (Ingresos)**. Dashboard (`/`) consume `GET /dashboard/summary`: stat cards, gráfico de gasto por categoría y comparación mensual (Recharts, lazy-loaded), presupuestos con progreso, top expenses y balances por cuenta. React Query Devtools activo solo en desarrollo.

**Escenarios (UI, Fase 2 punto 4)**: `ScenariosPage` (`/scenarios`, lista con ciclo de vida activar/desactivar/archivar/desarchivar/eliminar) y `ScenarioDetailPage` (`/scenarios/:id`, el composer) — cards de resumen derivado (`ScenarioSummaryCards`: totales mensual/6m/12m, cobertura de ingresos con barra de progreso, gastos esporádicos aparte, banner de "hay actualizaciones disponibles" cuando `hasUpdates`) más tres secciones (`ScenarioItemsSection`/`ScenarioIncomesSection`/`ScenarioCompositionsSection`) con selector para agregar productos/ingresos/escenarios existentes (excluyendo ya incluidos) y badge "Desactualizado" por ítem cuando `outdated`. Sin botón de sincronizar todavía — el endpoint `POST /sync` se pospuso deliberadamente (ver sesión de RFC-0022) y no existe aún en el backend. Nav (`Layout.tsx`) ahora incluye Escenarios/Productos/Ingresos junto al ledger existente, sin reestructurar en grupos (esa reorganización es el punto 7 del roadmap, aparte).

**Toda la UI del ledger está traducida al español**, incluyendo el Dashboard (RFC-0020) — stat cards, títulos de gráficos, tablas y estados vacíos — y los mensajes de validación de Zod (`z.config(es())`).

**Visión redefinida (ADR-0005, supersede parcialmente ADR-0004)**: Vectra es un **simulador de escenarios financieros**. Conceptos: **Escenario** (simulación nombrada con selección explícita de productos, composición con otros escenarios sin ciclos, estados activo/inactivo/archivado, proyecciones mensual/6m/anual derivadas), **Producto** (gasto único en el sistema — nombre, precio, frecuencia mensual/anual/esporádico — organizado por categorías, referenciado por escenarios, creable desde ambos lados), **Ingreso** (sección propia, frecuencias mensual/semanal/anual/esporádico, vínculo opcional bidireccional con escenarios, cobertura % consumido/restante). Principios: reutilizar antes que duplicar; **propagación con confirmación** (Vectra nunca modifica silenciosamente una simulación — si una categoría cambia, pregunta qué escenarios actualizar); comparación relativa al escenario activo (deltas); esporádicos aparte de proyecciones recurrentes. El ledger pasa a ser **vista de registro histórico** (sección secundaria del nav, no se borra código). Ver `docs/decisions/0005-financial-scenarios.md`, `product/vision.md`, `product/roadmap.md` y `glossary.md`.

**Interfaz orientada a preguntas, no a CRUD (ADR-0006, complementa ADR-0005 — no cambia el modelo de datos)**: cada pantalla principal responde una pregunta financiera concreta, con las métricas derivadas (mensual, 6 meses, anual, cobertura cuando aplica) como contenido principal y crear/editar/archivar como acción secundaria. Las cuatro preguntas: **Escenarios** → ¿cuánto cuesta este estilo de vida?; **Categorías** → ¿cuánto gasto en esta área?; **Productos** → ¿cuánto me cuesta mantener esto?; **Ingresos** → ¿cuánto me genera esta fuente? La ruta principal (`/`) pasa del Dashboard del ledger a Escenarios. `Account`/`Transaction`/`Report`/`Budget` se mantienen como herramientas del ledger histórico — `Budget` explícitamente **no** se marca como candidato a eliminar por ahora. Ver `docs/decisions/0006-question-driven-interface.md`.

## Qué se hizo en esta sesión

0. **ADR-0006 (documentación, sin código)**: tras un análisis de producto (sin RFC, sin implementación) sobre la experiencia de Vectra ya construida, se formalizó que las pantallas principales dejan de ser CRUDs y pasan a responder una pregunta financiera cada una (Escenarios/Categorías/Productos/Ingresos), con las métricas derivadas como contenido principal y crear/editar/archivar como acción secundaria. Decisiones cerradas en esta sesión: la ruta principal (`/`) cambia del Dashboard a Escenarios; los ingresos **no** se agrupan por categoría; `Budget` se mantiene, sin marcarlo como candidato a eliminar. `Account`/`Transaction`/`Report`/`Budget` siguen en el producto como ledger histórico. No cambia ningún modelo de dato ni endpoint — es una decisión de interfaz. `docs/decisions/0006-question-driven-interface.md`, `docs/product/roadmap.md` (Fase 2 reformulada) y este archivo actualizados; `docs/README.md` con la entrada del nuevo ADR en el índice.
1. **CRUD UI de Productos/Ingresos + composer de Escenarios (Fase 2, puntos 3-4)**: features `expense-items/`, `incomes/`, `scenarios/` en `apps/web/src/features/`, siguiendo 1:1 el patrón ya validado en `categories`/`transactions` (`*.api.ts`/`*.keys.ts`/`use-*.ts`/`*Page.tsx`/`*FormDialog.tsx`). `ScenarioDetailPage` (composer) agrega `ScenarioSummaryCards`/`ScenarioItemsSection`/`ScenarioIncomesSection`/`ScenarioCompositionsSection` como componentes de presentación separados. Rutas nuevas (`/expense-items`, `/incomes`, `/scenarios`, `/scenarios/:id`) y entradas de nav en `Layout.tsx`. Verificado: `pnpm typecheck`/`lint`/`build` en `apps/web` limpios; backend probado en vivo end-to-end contra un servidor real (`pnpm dev` en `apps/api`, smoke test vía `curl` creando categoría → producto → ingreso → escenario → `GET /scenarios/:id/summary`, resultado correcto). **No se pudo verificar visualmente en navegador**: este sandbox no tiene Chromium/Playwright/`chromium-cli` disponibles ni Docker; no hay skill de proyecto para levantar la app con un driver de browser. Pendiente que el usuario abra `pnpm dev` localmente y revise la UI a ojo antes de dar el composer por completamente validado.
2. **RFC-0022 (backend)**: feature `scenarios/` en `apps/api` — modelos `Scenario`, `ScenarioItem`, `ScenarioIncome`, `ScenarioComposition` (migración `20260729130000_add_scenarios`, aplicada en `vectra_dev` y `vectra_test`), CRUD de escenarios con ciclo de vida `ACTIVE`/`INACTIVE`/`ARCHIVED`, selección de productos/ingresos por snapshot, composición sin ciclos, endpoint `GET /scenarios/:id/summary` (totales, proyecciones, cobertura, `hasUpdates`), y guards de "archivar en vez de borrar" en `deleteExpenseItem`/`deleteIncome`. 13 tests nuevos, 170 en total pasando en `apps/api`. Mirror en `packages/types/src/scenarios.ts`.
   - **Limpieza de residuo**: se encontraron y eliminaron tablas/tipo (`scenarios`, `scenario_items`, `scenario_incomes`, `scenario_compositions`, `ScenarioStatus`) de un prototipo abandonado con diseño de "referencia viva" (contradecía ADR-0005), aplicadas localmente en `vectra_dev`/`vectra_test` en una sesión anterior bajo una migración (`20260729031005_add_scenarios`) que nunca llegó a `git`. Las cuatro tablas estaban vacías; se confirmó antes de borrar.
3. **Fix**: `formatDateOnly` (ahora en `packages/utils/src/date.ts`, compartido por Transactions y Dashboard) asumía un `date` sin hora (`"2026-01-15"`); el backend real devuelve ISO datetime completo (`"2026-07-20T00:00:00.000Z"`), lo que rompía la página de Transacciones (`RangeError: Invalid time value`). 5. **Feature**: traducción completa del ledger al español (nav, formularios, tablas, toasts, empty states, alert dialogs) + locale `es` de Zod para mensajes de validación por defecto.
6. **Feature**: `defaultCurrency` por defecto en el registro cambiado de `USD` a `COP` (backend y su mirror en `packages/types`).
7. **Docs**: ADR-0004 documentando el giro de producto hacia planes de gasto, con `vision.md`, `roadmap.md` y `glossary.md` actualizados.
8. **Merge**: se integró el PR #16 (RFC-0020 Dashboard) que había quedado divergido de esta rama de trabajo local; conflictos resueltos en `Layout.tsx` (nav en español + label "Dashboard"), `TransactionsPage.tsx` (usa `formatDateOnly`/`formatMoney` de `@vectra/utils`) y este archivo.

## Sigue

Reformulado por ADR-0006: el trabajo pendiente ya no es "completar el CRUD", sino transformar cada pantalla para que responda su pregunta (métricas derivadas al frente, gestión de datos secundaria).

1. **Categorías → "¿cuánto gasto en esta área?"**: falta el endpoint y la vista de totales (mensual/6m/anual) agregando los productos de la categoría, con la lista de productos como composición — hoy `CategoriesPage` sigue siendo CRUD puro del ledger.
2. **Productos → "¿cuánto me cuesta mantener esto?"**: `ExpenseItemsPage` no muestra el total mensual/6m/anual del producto ni en qué escenarios se usa (falta la relación inversa `ExpenseItem → Scenario[]`). Falta también la creación inline (de producto y de categoría) desde Categorías/Escenarios.
3. **Ingresos → "¿cuánto me genera esta fuente?"**: `IncomesPage` solo muestra el monto crudo; falta la proyección mensual/6m/anual (`ONE_TIME` no proyecta). Sin agrupación por categoría (decidido).
4. **Ruta principal → Escenarios**: cambiar `/` de `DashboardPage` a `ScenariosPage` (o al detalle del escenario activo) en `router.tsx`.
5. **Reorganización completa del nav**: dos grupos en `Layout.tsx` — primario (Escenarios/Categorías/Productos/Ingresos) y secundario "ledger histórico" (Cuentas/Transacciones/Presupuestos/Reportes-Dashboard), no la lista plana actual.
6. **Endpoint y UI de sincronización** (`POST /scenarios/:id/items/:itemId/sync` o similar): aplicar el precio/nombre nuevo del `ExpenseItem`/`Income` al snapshot — pospuesto a propósito en RFC-0022, es lo que le falta al badge "Desactualizado" para tener una acción asociada.
7. **Agregar una categoría completa a un escenario** de una sola vez (ADR-0005 §7) — hoy el composer solo permite producto por producto.
8. **Comparador de escenarios** con deltas contra el escenario activo (ADR-0005 §12, introduce Recharts).
9. **Validación visual manual** de lo ya construido (`ScenariosPage`/`ScenarioDetailPage`/`ExpenseItemsPage`/`IncomesPage`) en navegador — no se pudo hacer en este sandbox (sin Chromium/Playwright/`chromium-cli`/Docker). Golden path sugerido: crear producto → crear ingreso → crear escenario → agregar producto/ingreso → ver resumen → editar el producto y confirmar que aparece "Desactualizado".
10. **Arreglar** el test desactualizado de `apps/web/tests/features/dashboard/DashboardPage.test.tsx` (espera texto en inglés en una UI ya traducida al español) — preexistente, no bloqueante.

**Usuario de prueba con datos**: `dev@vectra.local` / `devpassword` (accounts, categories, transactions y budgets sembrados en USD).
